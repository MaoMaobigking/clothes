# 一、架构决策（想不通时回来看）

## 1.1 为什么不用 LangChain？851 行手写代码值得吗

**这个问题问过两次，所以值得写下来。**

先把账算清楚。LangChain 理论上能替代的部分（去掉空行和注释的净代码行）：

| 文件                            | 净行数  | LangChain 对应物           |
| ------------------------------- | ------- | -------------------------- |
| `services/ai/schemas.mjs`       | 208     | `withStructuredOutput()`   |
| `services/ai/client.mjs`        | 141     | ChatModel + 重试           |
| `services/ai/toolCore.mjs`      | 113     | Tool 定义                  |
| `services/ragService.mjs`       | 119     | TextSplitter + Retriever   |
| `services/ai/stream.mjs`        | 87      | streaming                  |
| `services/ai/tools.mjs`         | 79      | AgentExecutor              |
| `services/ai/provider.mjs`      | 53      | ChatOpenAI / ChatAnthropic |
| `services/embeddingService.mjs` | 51      | Embeddings                 |
| **合计**                        | **851** |                            |

**851 行是真的，LangChain 大概能砍掉 500~600 行。这个质疑站得住。**

但要看**这些代码的客户是谁**：

- 如果是产品团队交付功能 → 851 行自研胶水换 20 行 `create_react_agent`，该用，没有争议。
- 但这个项目的产出物是**一场面试对话**。代码本身就是交付物。

### 决定性的例子（2026-09-08 真实发生）

调 RAG 阈值时测出来的分数：

```
推荐几家附近的火锅店      0.1331   ← 无关，却分更高
通勤怎么穿显得专业        0.0995   ← 相关，却分更低
```

诊断：火锅店只命中「推荐」一个词，**查询向量只剩一维时余弦会被虚高**（一维向量和任何含该词的文档都完美对齐）。

**用 LangChain，20 行就能得到一个能跑的 RAG —— 然后永远不会发现这个问题**，因为根本不会去看分数分布。
面试官问「你的 RAG 检索不准怎么办」「阈值怎么定的」，只能答"框架默认的"。

《项目总纲》5.1 节的数据佐证就是这个意思：_2026 年"简历只有 LangChain"是减分项，面试必问"你不用 LangChain 做过什么"_。

### 但要诚实：有两处 LangChain 确实该赢

1. **`schemas.mjs` 208 行**，是这批文件里最大的一个 —— JSON Schema 校验 + 归一化 + 三级兜底。
   这正是 `withStructuredOutput()` 一行干的事，而"原理"没什么可讲（就是校验和重试）。**手写的边际收益最低**。
2. **`chunkText` 很弱**：15 篇文档切出 15 个块，等于**根本没切**，检索粒度是整篇文档。
   LangChain 的 `RecursiveCharacterTextSplitter` 比它好。

### 三个反对整体迁移的实际理由

1. LangChain.js 的 agent API 两年换了三代（`initialize_agent` → `AgentExecutor` → LangGraph）。
   项目得在半年后的面试现场还能跑起来。
2. 多 50+ 个传递依赖，换来答不上来的抽象层。
3. 代码已经写完验过了。迁移成本不是"写 LangChain 版"，是"重写 + 重新验证 + 丢掉 debug 故事"。

### 一个容易忽略的事实

**2026 年的行业趋势其实是在离开重型编排框架**，转向直接调 SDK + 用 MCP 做工具互操作。
现在这套（直调 + 官方 MCP SDK）不是"不懂所以没用框架"，恰恰是很多团队从 LangChain 疲劳里走出来后落到的位置。

### 关键区分：用 embedding API ≠ 用 LangChain

2026-09-08 把 RAG 从 TF-IDF 换成了 `text-embedding-v3`。分工是：

|                                | 归谁                             |
| ------------------------------ | -------------------------------- |
| 切块 / 检索 / 阈值 / 拼 prompt | **手写**（这些是能讲原理的部分） |
| 文本 → 向量                    | 调 API（这本来就该是模型的活）   |

手搓 TF-IDF 证明的不是"我懂 AI 工程"，而是"我没用 embedding"。
但手写 tool-calling 循环证明的确实是前者 —— 两件事要分开看。

> **面试怎么讲**：不要说"我没用 LangChain"，要说
> "编排逻辑我手写，因为那是我能讲原理的部分；向量化这种模型能力我调 API。
> 中间踩过一个坑：TF-IDF 时无关查询分数反而更高，因为单词命中会让余弦虚高 ——
> 我先用停用词表压住，后来换 embedding 才根治。"

## 1.2 为什么 get_weather 要做成工具，不直接问模型

**当时的疑问**：能不能直接用 DeepSeek 查天气，省一个 OpenWeather key？

**不能，而且这个"不能"正是 tool-calling 存在的理由。**

DeepSeek 是大语言模型，不是天气数据源：训练数据是静态的，chat completions 接口也不联网。
直接问它「北京今天几度」，它会**编一个看起来很真的数字**——比 mock 更糟，mock 至少一眼假。

工具调用的全部意义：**把模型不可能知道的事实，交给一个真实数据源**。天气是教科书级例子。

> **面试怎么讲**：问到"为什么天气要做成工具而不是直接问模型"，这就是标准答案。
> 补一句实现细节更好：工具返回值里带了 `source`（`located` 实时 / `fallback` 推算），
> 让模型知道这条数据的可信度，而不是把降级值当实时天气斩钉截铁地讲给用户。

## 1.3 MCP 进程里没有 userId，身份从哪来

**现象**：给 MCP 工具接真实数据时发现，`profileService.getLatestProfile(userId)` 第一个参数就是 `userId`，
但 MCP 是独立的 stdio 进程 —— 没有 HTTP 请求、没有 `Authorization` 头、没有 JWT 中间件，`executeTool` 拿不到任何身份。

**三条路，只有一条对**：

| 方案                                     | 评价                                      |
| ---------------------------------------- | ----------------------------------------- |
| 工具 `inputSchema` 加 `userId`，让模型填 | ❌ **模型可以填任意值 = 水平越权**        |
| 启动时从 `MCP_USER_ID` 注入，进程级锁定  | ✅ 语义正确：一个 MCP 进程 = 一个用户会话 |
| 环境变量传 JWT，启动时验签解出 userId    | ✅ 进阶版，多用户场景要用                 |

关键认知：**身份在 connect 之前就确定，不在工具参数里。**

实现细节：缺 `MCP_USER_ID` 时 `process.exit(1)`，**不给默认值**。默认成 1 就又变回《总纲》骂的"userId 写死"，隔离等于没做。

> **面试怎么讲**：
> "MCP 是独立 stdio 进程，没有 HTTP 上下文，拿不到 JWT 里的 userId。我一开始想做成工具参数，
> 但立刻意识到模型可以填任意值 —— 那就是水平越权。所以改成启动时注入、进程级锁定身份。
> 同一套 service 和 repo，HTTP 入口从 JWT 拿 userId，MCP 入口从启动配置拿，
> `WHERE user_id = ?` 这道边界两边都守住。"
>
> 这段话里有：协议理解、安全意识、分层设计、以及一个自己否掉的方案。比列工具名值钱得多。

## 1.4 为什么还在用已弃用的 Server 类

**现象**：IDE 提示 `@modelcontextprotocol/sdk` 的 `Server` 已弃用，建议用 `McpServer`。

**实测结论（SDK 1.29.0，2026-09-08）**：`McpServer.registerTool` 的 `inputSchema` **只接受 Zod**
（类型上是 `AnySchema = z3.ZodTypeAny | z4.$ZodType`）。传裸 JSON Schema 运行时直接抛：

```
inputSchema must be a Zod schema or raw shape, received an unrecognized object
```

**为什么这是个问题**：本项目的工具 schema 要同时喂两个消费者 ——

- MCP 的 `tools/list`（`inputSchema`）
- OpenAI 的 `tools[].function.parameters`（`GET /api/chat/tools` 直接吐给前端）

后者只认 JSON Schema。改成 Zod 优先就得用 `z.toJSONSchema()` 转回去，而它会多塞
`$schema` 和 `additionalProperties: false` 两个键，得再摸掉才能保证前端契约不变
—— 等于为了消一个提示，给单一真源加一层需要人工消毒的转换。

`Server` 的弃用说明原话是 **"Only use `Server` for advanced use cases"**：
「一份 JSON Schema 同时供 MCP 和非 MCP 两侧」正是这种 case。

**⚠️ 别"顺手修警告"**，会把 `toolCore.mjs` 的单一真源撞碎。原因已写在 `mcp/server.mjs` 的代码注释里。

## 1.5 什么该放 repo，什么该放 service

这条是从两次重构里总结出来的判断标准：

> **换掉数据库要不要跟着改？要 → repo；不要 → service。**

| 放哪                     | 例子                                                                      |
| ------------------------ | ------------------------------------------------------------------------- |
| **repo**（换库就要重写） | `boolean → TINYINT(0/1)`、`数组 → JSON 字符串`、`空图片 → NULL`、SQL 本身 |
| **service**（产品决策）  | 默认名字/分类/配色、id 生成规则、校验规则、多步编排、越权校验             |

**为什么重要**：repo 里混业务规则，换库重写时会被迫跟着誊一遍，抄漏一条就是线上脏数据。
而且规则和它的校验被隔开在两层，[2.7](#27-默认分类-上衣-和枚举-top-对不上) 那个 bug 就是这么来的。

同一个标准的另一个应用：`weather.mjs` 从 `services/scene/` 提到 `services/` 顶层。
理由是它有了第二个消费者（AI 工具层），留在 `scene/` 会让 `services/ai/` 反向依赖 `services/scene/`，
读代码的人会以为工具依赖场景功能。

# 二、真踩过的坑

## 2.1 router.use(authRequired) 让登录接口自己要求登录

**现象**：给 AI 路由补鉴权时图省事写了 `router.use(authRequired)`，结果 `POST /api/auth/login-password`
返回 `{"error":"UNAUTHORIZED","message":"请先登录"}` —— **登录接口自己要求先登录**，死锁。

**根因**在 `index.mjs` 的挂载顺序：

```js
app.use('/api/garments', garmentRoutes)   // 独立前缀
app.use('/api', aiRoutes)                 // ← 裸 /api，且排在下面 15 个之前
app.use('/api/auth', authRoutes)
app.use('/api/profile', profileRoutes)
...
```

`router.use()` **不带路径就会匹配 `/api/*` 的每一个请求**。`aiRoutes` 排在 `authRoutes` 前面，
所以 `/api/auth/login-password` 先撞上 AI 路由器的鉴权中间件，401 之后不再 `next()`。

**解法**：逐路由挂 `authRequired`。

**关键认知**：`routes/garments.mjs` 能用 `router.use` 是因为它挂在 `/api/garments` 这个**独立前缀**下。
所以 `routes/ai.mjs` 原来那种逐路由写法**不是随意，是这个挂载方式逼的**。已写进代码注释防止后人"统一一下"。

> **面试怎么讲**：Express 中间件是按注册顺序线性执行的，`router.use(mw)` 的作用域是**挂载前缀**而不是"这个文件里的路由"。
> 一个挂在裸 `/api` 上的路由器，它的无路径中间件会拦下所有 `/api/*`，包括本该由后面路由器处理的请求。

## 2.2 四个烧钱的 AI 接口没有鉴权

**现象**：审计发现 `routes/ai.mjs` 里鉴权不一致：

| 路由                     | 改之前                             |
| ------------------------ | ---------------------------------- |
| `POST /api/chat`         | **无中间件**                       |
| `POST /api/chat/stream`  | **无中间件**                       |
| `POST /api/chat/rag`     | **无中间件**                       |
| `POST /api/chat/tools`   | `authOptional`（等于可无鉴权访问） |
| `POST /api/style-report` | `authRequired` ✅                  |

同一个文件里 `/style-report` 是 `authRequired` —— 所以这是**遗漏，不是设计**。

**放大风险的三个东西**：`app.use(cors())` 全开、`express.json({ limit: '12mb' })`、无限流。
合起来 = **任何人知道地址就能烧掉 `AI_API_KEY` 的额度**。

**⚠️ 一个命名陷阱**：`routes/ai.mjs` 里的 `requireKey()` 名字有误导性 ——
它只检查**服务端有没有配 key**，跟调用方身份毫无关系。别把它当鉴权。

## 2.3 LIMIT ? 报 ER_WRONG_ARGUMENTS

**现象**：把 `aiRepo` 里写好但从未被调用的会话函数接线之后，`GET /api/chat/sessions` 报：

```
ER_WRONG_ARGUMENTS: Incorrect arguments to mysqld_stmt_execute
```

**根因**：`LIMIT ?` —— **MySQL 预处理语句不接受 LIMIT 占位符**。

```js
// ❌ 报错
;(`... ORDER BY created_at DESC LIMIT ?`, [userId, Number(limit)])

// ✅ 夹紧成整数后内联（数字已 clamp，没有注入面）
const safeLimit = Math.max(1, Math.min(Number(limit) || 30, 100))`... ORDER BY created_at DESC LIMIT ${safeLimit}`,
  [userId]
```

有意思的是，**同一个文件里的 `listStyleReports` 反而写对了** —— 因为它一直在被调用。
`listChatSessions` / `listChatMessages` 是死代码，从来没跑过，所以 bug 一直藏着。

> **教训**：**死代码不算写完的代码。** 没跑过的代码里有 bug 是常态，不是意外。
> `chat_sessions` / `chat_messages` 两张表建了、六个 repo 函数写了、注释都写全了 ——
> 但零调用，所以两个 SQL bug 一直在那儿。这也是《总纲》"存了才是产品"那条的另一面：
> 写了不接线，等于没写。

## 2.4 RAG：无关问题的分数比相关问题还高

**现象**（TF-IDF 时期）：想加个相关度阈值挡掉无关问题，实测发现**单一阈值切不开**：

```
相关问题 top1 最低:  0.0995  （通勤怎么穿显得专业）
无关问题 top1 最高:  0.1331  （推荐几家附近的火锅店）
                     ↑ 两者重叠 -0.0337
```

定 0.1 会**既放过火锅店、又挡掉通勤穿搭**，两边都错。

**根因**：火锅店那句只命中一个泛词「推荐」（idf=2.16，文档里很常见）。
**查询向量只剩一维时余弦会被虚高** —— 一维向量和任何含该词的文档都完美对齐。
而"通勤怎么穿显得专业"命中两个词（通勤、专业），分数反而更低。

这是 TF-IDF + 余弦的经典病理：**余弦归一化掉了"证据的量"**。

**第一次解（band-aid）**：查询侧停用词表，去掉「推荐/帮我/怎么/什么…」这类提问用语。
效果立竿见影 —— 无关问题命中数全部归零，两类彻底分开（相关最低 0.0943 / 无关最高 0.0000）。
但注释里得老实写"知识库文档数量变化后要重新标定"，**是负债不是资产**。

**第二次解（根治）**：换 `text-embedding-v3` 语义向量。停用词表整个删掉。

最能说明差别的两条 —— TF-IDF 永远匹配不到，语义版直接命中：

| 查询                               | 命中             | 分数   |
| ---------------------------------- | ---------------- | ------ |
| 我个子矮腿短有什么办法看起来高一点 | 02-小个子穿搭.md | 0.7179 |
| 上班穿得体一点但别太死板           | 01-通勤穿搭.md   | 0.7158 |

两句都**不含文档里的关键词**。

**阈值标定方法**（换模型/换语料后照着重跑）：

1. 准备两组问题 —— 一组领域相关、一组完全无关（写代码/点外卖/查签证…）
2. 打印每个问题的 top1 分数
3. 取「相关组最低分」和「无关组最高分」之间的中点
4. **两组如果重叠，说明检索本身有问题，调阈值治不了，得先看检索**

实测（text-embedding-v3 / 1024 维 / 15 篇文档）：相关 0.5632~~0.8637，无关 0.3418~~0.4544，取 **0.50**。

**一个诚实的边界**：「明天开会该准备什么材料」拿到 0.5755，会过线命中「面试穿搭」。
没有把阈值抬到 0.58 挡它，因为它本来就是灰区（在穿搭 App 里问这句，想要穿搭建议是合理解读），
而抬到 0.58 会连「冷白皮适合什么颜色」(0.5632) 一起挡掉。
**宁可放过灰区、不可漏掉真相关** —— prompt 里已经写了"资料没有的直接结合知识补充"。

> **⚠️ 阈值不能跨模型搬**：不同 embedding 模型的余弦分布不一样。换模型/换维度必须重新标定。
> 索引缓存里存了 `model` 和 `dim`，不一致会自动重建 —— 否则旧向量和新查询不在同一个空间，
> 算出来的余弦是没有意义的数字。

## 2.5 冒烟脚本断言写死了 mock 的值

**现象**：`get_weather` 从 mock 换成真实数据后，`npm run check:ai` 的 Function Calling 项失败。

**根因**：`scripts/checkAi.mjs` 的断言是 `toolReply.includes('25°C')` ——
**25°C 是 mock 里北京写死的那个值**。天气变真之后温度每天都不一样，这条断言必然失败。

**解法**：断言"工具真被调了、结果真被消费了"，而不是绑具体数值：

```js
const mentionsCity = toolReply.includes('北京')
const mentionsTemp = /-?\d+\s*°?C/.test(toolReply)
check('工具结果被模型正确消费', mentionsCity && mentionsTemp, ...)
```

> **教训**：测试断言绑在 mock 的具体返回值上，等于把"实现细节"写进了契约。
> mock 换真实数据时，测试会以一种看起来像"功能坏了"的方式失败，浪费排查时间。
> **断言要针对行为，不针对数值。**

## 2.6 颜色筛选永远返回 0 条

**现象**：`POST /api/chat/tools` 里模型传了 `color` 参数就一条都查不到。

**根因**：过滤写的是 `(g.color || '').includes(color)`，但 `garmentRepo.rowToGarment`
产出的字段是 `primaryColor` / `secondaryColors`，**根本没有 `color` 这个字段**。
`undefined || ''` 恒为空串，所以一律过滤成 0 条。

同一处的 `g.tags` 同理是死代码 —— 也没有 `tags` 字段。

**解法**：改用 `primaryColor` + `secondaryColors` 匹配。

> **教训**：这类 bug 静默失败（返回空数组，不报错），比抛异常难查得多。
> 写跨层取字段的代码时，去 repo 的映射函数里对一眼实际字段名 —— 不要凭印象。

## 2.7 默认分类 '上衣' 和枚举 'top' 对不上

**根因**：`garmentRepo.addGarment` 里默认分类写的是 `'上衣'`，而 `garmentService` 的
`ALLOWED_CATEGORIES` 只认 `'top'`。`'上衣'` 是**前端 `WARDROBE_CATEGORIES` 里的显示 label，不是枚举 key**。

两处隔着一层，没人发现它们对不上，于是不带 `category` 的新增会写进一个
**既不是 key、也通不过后续 PATCH 校验**的值。

**解法**：默认值上移到 service 的 `applyGarmentDefaults()`，和 `ALLOWED_CATEGORIES` 放在同一个文件里 —— 让它们看得见彼此。

> **这个 bug 的成因本身就是分层错位**（见 [1.5](#15-什么该放-repo什么该放-service)）。
> 修法不是"改个字符串"，是"把默认值和校验规则放到一起"。

**⚠️ 还有一个同类的没修**：`season` 的默认值 `'四季'` 和 `WARDROBE_SEASONS` 的英文 key 同样对不上。
但 `rowToGarment` 拿它兜 `seasons` 的底（`seasons` 为空时回退成 `[season]`），改动波及面更大，单独再修。

# 三、环境与工具链的坑

## 3.1 MySQL 在 3308，但 Docker Desktop 不自启

- 容器 `lingxi-mysql8`（MySQL 8.4.11）→ `localhost:3308`，卷 `lingxi-mysql8-data`
- 带 `--restart unless-stopped`，但 **Docker Desktop 本身不会自启**（实测中途退过一次，
  表现是 `ECONNREFUSED 127.0.0.1:3308`）。**开发前先起 Docker。**
- 本机还有个 MySQL80 服务在 **3307**（`my.ini` 里配的），密码和项目 `.env` 里的不一样。
  别混。

## 3.2 git 代理端口：Clash Verge 是 7897 不是 7890

**现象**：`git push` 报 `Failed to connect to 127.0.0.1 port 7890`，但代理明明开着。

**根因**：Clash Verge 新版把默认混合端口从 **7890 改成了 7897**，git 的配置还停在旧值。

```bash
git config http.proxy  http://127.0.0.1:7897
git config https.proxy http://127.0.0.1:7897
```

**⚠️ 当前只改了本仓库级，全局配置仍是 7890** —— 其它仓库 push 会踩同一个坑。
想一次性修掉加 `--global`。

诊断命令：`netstat -ano | grep LISTENING | grep 789` 看代理实际在哪个端口。

## 3.3 Windows 下 pkill 杀不掉 node，要按端口杀

**现象**：改完代码重启服务，测出来还是旧行为 —— 因为 `pkill -f "node ... index.mjs"`
在 Windows 的 Git Bash 里匹配不到，旧进程还占着 8787，新进程 `EADDRINUSE` 直接退出，
而测试打的是旧进程。**一度以为是自己的修改没生效。**

```bash
PID=$(netstat -ano | grep LISTENING | grep ":8787" | head -1 | awk '{print $NF}')
taskkill //PID "$PID" //F
```

**教训**：重启后先确认端口真的换了进程，或者 `grep -c EADDRINUSE` 看一眼启动日志。

## 3.4 其它小坑

| 坑                                          | 解                                                            |
| ------------------------------------------- | ------------------------------------------------------------- |
| `node -e` 里写 top-level `await` 报编译错   | 加 `--input-type=module`                                      |
| Git Bash 的 `/tmp` 和 node 看到的不是同一处 | node 会把 `/tmp/x` 解析成 `E:\tmp\x`，用项目内相对路径        |
| Windows 终端传中文给 curl 会变乱码          | 不是应用 bug。用 `--data-binary @file.json` 传 UTF-8 文件验证 |
| `stdout` 打日志会让 MCP 客户端解析失败      | stdio 传输把 stdout 当 JSON-RPC 通道，**日志只能走 stderr**   |
| 父进程的 `--env-file` 不会传给子进程        | `StdioClientTransport` 要显式传 `env: process.env`            |
| 百炼 embedding 单次超过 10 条报 400         | `InvalidParameter`，批量上限是 10（2026-09-08 实测）          |
| 格式化 `rag-docs/*.md` 会触发索引全量重建   | 缓存靠 mtime 判失效，别对知识库跑 prettier                    |

# 四、能力矩阵：能讲 vs 不能吹

> 对应《项目总纲》7.2 节。**面试照这张表讲，不要多说一个字。**

## AI 能力 × Provider

| 能力                                 | OpenAI 兼容（含 DeepSeek） | Anthropic               |
| ------------------------------------ | -------------------------- | ----------------------- |
| 普通对话                             | ✅ 已实测                  | ⚠️ 已实现，**未实测**   |
| 结构化输出（JSON Schema + 三级兜底） | ✅ 已实测                  | ⚠️ 已实现，**未实测**   |
| SSE 流式                             | ✅ 已实测                  | ⚠️ 已实现，**未实测**   |
| 工具调用（手写循环）                 | ✅ 已实测                  | ❌ **未实现**（待接入） |

- **「已实现，未实测」**= 代码按官方 API 形状写了（`client.mjs` 的 `structuredAnthropic` / `callAnthropic`、
  `stream.mjs` 的 `streamAnthropic`），但**手上没有 Anthropic key，一次都没真跑过**。
  不能当"支持"讲。
- **「未实现」**= `tools.mjs` 的 `aiChatWithTools` 只写了 OpenAI 兼容协议。
  Anthropic 的工具协议形状不同（`tool_use` / `tool_result` 内容块 + `stop_reason` 判定），需要单独一条分支。

**为什么不干脆删掉 Anthropic**：那些实现是照真实 API 形状写的，删掉是更大更有风险的改动，拿到 key 就能验。
**标注"未实测"比删掉更诚实，也比假装支持更诚实。** 面试照矩阵讲反而是加分项。

**为什么不留静默陷阱**：`aiChatWithTools` 已在入口显式抛 `TOOL_CALLING_UNSUPPORTED_PROVIDER`（501）。
补这个守卫之前，`AI_PROVIDER=anthropic` 会把 OpenAI 形状的请求发到
`https://api.anthropic.com/chat/completions` 并带错认证头，报出来是个让人摸不着头脑的 404/401 ——
看着像网络或密钥问题，实际是"这条路根本没实现"。**静默陷阱比明确不支持难查得多。**
