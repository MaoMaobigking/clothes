# H5 性能基线与优化对比

> 测量时间：2026-09-11　分支：`refactor/miniapp-architecture`
> 原始报告：`docs/perf/base-desktop-{1,2,3}.json`（优化前）· `docs/perf/after-desktop-{1,2,3}.json`（优化后）

## 怎么复现

```bash
cd miniapp && npm run build:h5
cd dist/build/h5 && python -m http.server 5055
# 另开终端，跑 3 次取中位数
npx --yes lighthouse http://localhost:5055/ --preset=desktop --quiet \
  --chrome-flags="--headless=new --no-sandbox" \
  --output=json --output-path=docs/perf/xxx.json
```

⚠️ **必须跑 3 次取中位数** —— 原因见下面「一个差点上简历的错误数字」。

---

## 结果

| 指标                     | 优化前（3 次中位数） | 优化后（3 次中位数） |
| ------------------------ | -------------------- | -------------------- |
| Performance 总分         | 96                   | **97**               |
| Largest Contentful Paint | 1.3 s                | **1.1 s**            |
| First Contentful Paint   | 0.7 s                | 0.7 s                |
| Cumulative Layout Shift  | 0.001                | **0**                |
| Total Blocking Time      | 0 ms                 | 0 ms                 |

三次原始值：

|            | 第 1 次   | 第 2 次 | 第 3 次 | 极差      |
| ---------- | --------- | ------- | ------- | --------- |
| 优化前 LCP | **2.7 s** | 1.3 s   | 1.3 s   | **1.4 s** |
| 优化后 LCP | 1.2 s     | 1.1 s   | 1.1 s   | **0.1 s** |

### ⭐ 真正的收益是「方差」，不是中位数

中位数只从 1.3 s 降到 1.1 s，**但最差情况从 2.7 s 降到 1.2 s，极差从 1.4 s 收敛到 0.1 s。**

原因很直接：优化前首屏 LCP 元素**依赖一个跨域 API**，所以 LCP = 网络状况的函数；
云函数冷启动那一次就是 2.7 s。优化后首屏**零 API 请求**，LCP 只取决于本地静态资源，
所以三次几乎一样。

**诚实的表述**：这不是「把页面变快了一倍」，是「把首屏从网络波动里摘出来了」。
P95 / 最差体验的改善远大于中位数。

## 做了什么

### ① 演示账号列表改为按需展开（主要收益）

`pages/login/index.vue`：原来 `onMounted` 里直接 `loadDemoAccounts()`，
而列表里的 `description` 文字正好是首屏**最大的可见元素** → LCP 被那个请求锁死。

实测那个请求：**1988 ms XHR + 449 ms CORS 预检**。

改成默认折叠、点开才拉。**不是为了刷分**：演示账号是规格 §5.4 的**兜底入口**，
主路径是账号密码登录。兜底入口不该在首屏发两秒的请求，更不该是首屏最重的内容。
代价是评委现场多点一下。

效果：LCP 元素从 API 文本变成静态的品牌副标题「登录后你的衣橱、画像和搭配都会留在账号里」，
**首屏网络请求里零 API**。

### ② `preconnect` / `dns-prefetch` 到 API 域名

`vite.config.ts` 新增 `preconnectApi` 插件，用 `transformIndexHtml` 注入。
Lighthouse 在基线里点名这一条，估算省 199 ms。

两个实现细节：

- **只在跨域时注入**。H5 默认 `VITE_API_BASE_URL` 为空（同源走 Vite proxy），同源做 preconnect 没意义
- **必须带 `crossorigin`**。XHR/fetch 是 CORS 请求，不带这个属性预热的是「非 CORS 连接」，
  实际请求时浏览器会另开一条，preconnect 白做 —— 这是这条优化最常见的写错方式

---

## ⚠️ 一个差点上简历的错误数字

**最初只跑了 1 次基线，拿到 `88 分 / LCP 2.3 s`。**
按那个数对比优化后的 97 / 1.1 s，会得出「LCP 2.3 s → 1.1 s，提升一倍」的结论。

**那是错的。** 补跑 3 次基线后发现真实中位数是 `96 / 1.3 s` ——
最初那次是运气差的一次（云函数冷启动）。

教训有两条，都值得记：

1. **性能测量必须多次取中位数。** 单次结果在有网络依赖时可以差出 2 倍
2. **越是要写进简历的数字，越要先想「被追问一句『你跑了几次』会怎样」。**
   `2.3 → 1.1` 听起来漂亮，但站不住；`方差从 1.4 s 收敛到 0.1 s` 数字小，但经得起查

## 测量边界（必须一起说）

1. **测的是登录页，不是应用主界面。** 未登录 → 首页重定向到 `/login`。
   这是真实的「首次冷访问」场景，但不代表登录后的主流程。要测主界面得先注入 token，本轮没做
2. **打的是线上云后端**（`express-q6b8-*.sh.run.tcloudbase.com`），含公网往返与云函数冷启动
3. 只有 desktop preset，没跑移动端
