## 批次 1 · 前端接上流式对话 ✅ 已完成（H5 端）

| 成本 | 后端已经全通，只差客户端                                                  |

### 做了什么

**1.0 只做了 H5 端。** 小程序的 `uni.request` 是请求-响应模型，拿不到中间分片；
微信另有 `enableChunked` + `onChunkReceived`，但**没真机验证过就不做不写**，这条结论没变。
`SUPPORTS_CHAT_STREAM` 用条件编译在小程序端编译成 `false`，小程序继续走 `/api/chat` 一次性返回。
（已验构建产物：mp-weixin 包里该常量是 `(()=>!1)()`，页面也确实走的降级分支。）

**1.1 分块边界处理 —— 实际是两层，不是一层。** 这是做下去才发现的，也是最能讲的一点：

| 层       | 断在哪              | 症状                   | 修法                                |
| -------- | ------------------- | ---------------------- | ----------------------------------- |
| 字节边界 | 一个 UTF-8 字符中间 | **中文乱码**，且无报错 | `TextDecoder` 开 `stream: true`     |
| 消息边界 | 一条 SSE 事件中间   | **JSON.parse 抛异常**  | 缓冲 + 按行喂 + 空行派发 + 残片续拼 |

两层独立，各修各的。**只修第 2 层，中文照样乱码**——因为拼起来的已经是坏字符了。
关键细节：整条流必须复用**同一个** decoder 实例，每片新建等于 `stream: true` 没开。

解析按 WHATWG 的 server-sent events 算法写，不是「按空行切一刀」——后者遇到
CRLF 结束符、多行 data、心跳注释行都会错，而这三样服务端随时会给。
另外处理了一个刁钻情况：**分片末尾是孤立的 CR 时必须扣住不切**，
它可能是 CRLF 的前半截，当场切会凭空多一个空行，且只在分片恰好落在那儿时复现。

**1.2 中途停止。** `AbortController` → fetch 断开 → 后端 `res.on('close')` → 中止模型调用。
语义上特意做成：abort 后**不抛异常**，带着已生成的部分正常返回（`aborted: true`）——
用户点停止不是出错，已经吐出来的字是有效内容。离开页面也会自动停（`onUnmounted`）。

**1.3 异常重连：没做。** 所以简历里**删掉了「异常重连」**（见批次 0）。
解析器把 `id` 字段按规范做了跨事件保留，重连要做的话地基在，但没做就是没做。

### 顺手修掉的一个真 bug

`sendChat` 从不回传 `sessionId`，服务端 `ensureSession` 只好**每条消息新建一个会话** ——
聊十句在库里就是十个会话，会话列表接口等于废了。现在流式和非流式都带上 sessionId 续聊。

## 批次 2 · 可访问性最小可信版 ✅ 已完成

### 为什么必须做

JD 要求 4 原文：**「深刻理解可用性、可访问性」**。
你现在是零。被问到只能承认，而这是 JD 白纸黑字写的要求——**承认一条明写要求为零，比承认 SSR 没做过严重得多**。

### 一条贯穿始终的前提（要主动说）

**这套东西只在 H5 端成立。** 小程序没有 DOM、没有键盘焦点模型，没有 Tab 也没有 Esc，
焦点陷阱在那边无从谈起。所以全部用条件编译隔离，小程序端零运行时开销。
——这本身就是个可讲的点：**先判断「这个需求在这个端上存不存在」，再动手。**

### 2.1 键盘可达 ✅

登录页 5 个自定义按钮（登录 / 微信登录 / 演示账号折叠 / 演示账号项 / 开发身份）
原来全是 `<view @tap>`：鼠标能点，键盘 Tab 不到、回车不触发、读屏器只念「一段文字」。
现在补上 `role="button"` + `tabindex` + `@keydown`。

**为什么不直接换成 `<button>`：** 小程序端 `<button>` 是原生组件，自带一套改不掉的
样式和层级行为，全站 30+ 处按钮的视觉要重对一遍。补语义远比换标签便宜。

**踩到的坑（值得讲）：** 第一版写的是 `v-bind="buttonA11y(fn)"` 一句话搞定，
**小程序端编译直接失败**：`[vite:vue] v-bind="" is not supported.`
WXML 要在编译期把属性名静态列出来，没有「运行时展开一个对象」这回事。
退回逐个属性写之后两端都过。—— 跨端开发里「H5 能跑」不等于「能编译」。

细节：空格键必须 `preventDefault()`，否则按钮被激活的同时页面还会滚下去一屏。

### 2.2 焦点管理 ✅（最能讲的一条）

做在 `components/Sheet/Sheet.vue` 上——它是全站弹层的公共组件，**5 个调用点一次全好**。
这正是当初把 14 处手写遮罩收敛成组件的回报，也是「组件化的收益什么时候才兑现」的实例。

三件事成套做，少一件就是半残：

1. 打开时把焦点移进弹层（否则要一路 Tab 穿过整个背景才进得来）
2. 打开期间 Tab 不许逃逸，走到头绕回开头（**焦点陷阱**）
3. 关闭时把焦点**还给触发它的那个元素**（最容易漏，但它是连续操作体验的关键）

第 3 条还有个细节：归还前要判断那个元素**还在不在文档里**——它可能随某个 `v-if` 一起消失了，
对脱离文档的元素 `focus()` 是静默失败，焦点会掉回 `<body>`。

**Esc 无条件关闭，不看 `maskClosable`。** 遮罩点击可以禁用（防填表误触），
但键盘必须留出路，否则就是 WCAG 2.1.2 说的**键盘陷阱**：进得去出不来。
而误按 Esc 远比误触遮罩难发生，两者风险不对等。

### 2.3 语义与替代文本 ✅

- 两个输入框补 `aria-label`：**「用 placeholder 当标签」是最典型的 a11y 反模式**
  ——一开始输入它就消失了，读屏器也未必念它
- 错误/提示加 `role="alert"` / `role="status"`：否则键盘用户按下登录后毫无反馈
- 装饰性箭头 `›` 标 `aria-hidden="true"`
- 弹层加 `role="dialog"` + `aria-modal="true"` + `aria-label`
- 折叠头加 `aria-expanded`

  已把精确比值用测试钉住，等设计侧拍板。**若要改：主色压到 #c24677（原值 76%）得 4.73:1 过 AA。**

> 2 组标准豁免、5 组是真问题但属于设计决策，我把它们钉在测试里等拍板」。

> 和真机行为对不上，测了反而给人虚假信心。这一点已写在 spec 的注释里。

## 批次 3 · 工具调用过程可视化 ⚠️ 3.1 / 3.2 已完成，3.3 只做了地基

### 为什么

这是简历上那句「调用过程在前端可视化」的兑现，也是**AI 前端唯一能做在前端的部分**。
后端的工具调用循环已经写好（最多 5 轮），欠的是把每一轮的状态推给前端并渲染。

### 3.1 后端推过程事件 ✅

`aiChatWithTools` 加了第 5 个参数 `onStep`，每个工具**执行前后各推一条**：

| 事件         | 时机       | 带什么                      |
| ------------ | ---------- | --------------------------- |
| `tool_start` | 执行**前** | round、工具名、模型填的入参 |
| `tool_end`   | 执行**后** | round、工具名、结果摘要     |

**为什么分两条、且 start 必须在执行前推**：工具本身可能跑好几百毫秒
（查衣橱要落库查询）。只在执行完推一条的话，这段时间界面上什么都没有，
用户只看到一个转圈。先推「我要去查衣橱了」，界面立刻有东西显示。

两个实现细节：

- **结果摘要在后端截到 120 字**，不推全文。工具结果可能是整个衣橱的 JSON（几十 KB），
  那是喂模型的上下文不是给人看的——原样推等于把最贵的数据在 SSE 上再发一遍，而界面只显示一行。
- **`emitStep` 把回调异常吞掉**。onStep 实际是往 SSE 里 write，连接断了会抛；
  让它冒出去会中断整个工具循环，但「播报失败」不该决定「模型这轮跑不跑完」。

顺手补了 `/chat/tools` 缺的 `X-Accel-Buffering: no`（`/chat/stream` 早就有）。
不加这条，nginx 会把步骤事件攒起来一起发，「过程可视化」退化成「等半天一次性出现」，等于没做。

### 3.2 前端步骤条 ✅

`components/ToolSteps/ToolSteps.vue`：折叠显示「正在查你的衣橱…」，展开显示每轮的
工具名、入参、返回摘要。前端把 start/end 两条合并成一行，用「end 到没到」判断这步跑完没有。

**一个边界**：同一轮里同名工具可能被调用多次（模型一次要两个城市的天气）。
用 `round+name` 做 key 会把它们叠成一条，所以 start 每来一条就新建一行，
end 去补**最后一条还没结束的**同名步骤。

a11y 上顺手做对了两处（承批次 2）：折叠头是可聚焦的 `role="button"` + `aria-expanded`；
运行状态不只用颜色区分，还换图标（`◐` → `✓`），否则过不了 WCAG 1.4.1。

### 3.3 Markdown 容错 ⚠️ **函数和测试做完了，但没有接入点**

`utils/markdown.ts` + 27 条单测已完成：补全未闭合的代码围栏和行内标记，
其中最要紧的是**围栏**——没闭合会让解析器把后面所有正文都吞成代码块，
表现是正文突然整段变灰底等宽字，下一帧又唰地变回去。

**但它现在没有调用点。** 原因是查下来发现：**本项目根本没有 Markdown 渲染器。**
聊天气泡是纯文本渲染（`white-space: pre-wrap` 直接输出），
没装 marked / markdown-it，也没用 `<rich-text>`。没有「渲染」这一步，
也就没有「渲染前预处理」这个插入点。

要真正接上，得先给气泡做一个跨端 Markdown 渲染器（小程序侧只能走 `<rich-text>`），
那是独立的一块工作量，不是「顺手做」。

> ⛔ **在接上渲染器之前，简历和面试都不要说「做了流式 Markdown 容错」。**
> 能说的是：「我知道流式 Markdown 会因为未闭合围栏整段闪烁，
> 补全逻辑和测试我写好了，但这个项目的气泡还是纯文本渲染，所以没接上去。」
> —— 说到这个程度反而比含糊带过更可信。

### 诚实边界（讲的时候必须带上）

- 工具调用这条路**目前仍不是真流式**，最终文本是一次性推的，我推的是每一轮的状态事件。
  所以 `streamChatWithTools` 的注释里把这条写死了，防止以后自己看代码看串。
- **Anthropic 的工具协议没接**，切过去会显式抛 501 并说明原因——这是我主动加的守卫，
  在这之前它会带着 OpenAI 的请求形状发到 Anthropic 地址，报一个看着像密钥问题的 404
- 工具模式**默认关闭**：实测 tool-calling 的 prompt token 是普通对话的 20 倍，
  默认开就是默认按 20 倍烧钱，而大部分问题不需要查衣橱。开关上直接写了成本提示。

### 验收标准

## 批次 4 · 状态管理讲得出深度 ✅ 已完成

阿里侧重三件套之一，但原来对 Pinia 只能讲「我用了」。
目标不是重构，是**找到项目里一个真实的状态管理问题并解决**。

### 找到的问题：换账号时心愿单不清，跨账号泄漏

`stores/auth.ts` 的 `purgeUserScopedCaches()` 在换人/退出时会 reset
profile、wardrobe、cart 三个 store，**但漏了 wishlist**。

**为什么这是真 bug 而不是洁癖：**

pinia store 是**模块级单例**。`uni.reLaunch` 会重建页面栈，但 store 实例和里面的数据
一条都不会变。所以「清了本地缓存 + 跳回登录页」看起来很干净，
上一个人的内存数据其实原封不动。

而心愿单**比其他三个更严重**：

| store    | 漏清的后果                                                                     |
| -------- | ------------------------------------------------------------------------------ |
| cart     | 新账号先看到上一个人的车，但下次拉取会被覆盖                                   |
| wardrobe | 同上，有请求会刷新                                                             |
| wishlist | **纯内存、不落库、没有任何请求会刷新它** —— 上一个人标的爱心会一直留到进程结束 |

**恰恰因为它「只是个本地数组、没接后端」，反而没有任何兜底机制能纠正它。**
落库的那几个至少还有下一次拉取兜底，它连这个都没有。

### 改法与代价

一行 `useWishlistStore().clear()`，加上把「必须穷举所有装用户数据的 store」
写进注释——因为这类 bug **不报错、不白屏**，只有真换号点进商城才发现，
靠 code review 抓不住，只能靠一句显式的提醒。

代价：`auth` store 对其它 store 的依赖又多了一条。
这是这个设计固有的成本——「谁来负责清理」要么集中在 auth（现在这样，容易漏），
要么让每个 store 自己订阅登出事件（不会漏，但要引入事件总线）。
当前规模下集中式更简单，**但漏一个就是一条数据泄漏，这个取舍要能说清楚。**

### 产出的简历 bullet

> 定位并修复一处跨账号状态泄漏：pinia store 是模块级单例，`reLaunch` 重建页面栈
> 但不重建 store，换账号时纯内存的心愿单不会被任何请求刷新，会一直留到进程结束；
> 收敛登出清理的职责边界并注释了「集中清理 vs 各自订阅」的取舍。

## 计划外：后端也在解析 SSE，而且有同一个 bug ✅ 已修

做完批次 1 回头看后端时发现的，**不在原计划里**，但直接影响批次 1 的演示效果。

后端既是 SSE 的**服务端**（对前端），也是 SSE 的**客户端**（对模型 provider）。
读上游流时 `server/services/ai/chat/stream.mjs` 两处都是这么写的：

```js
const chunk = decoder.decode(value, { stream: true })        // ✅ 字节边界挡住了
for (const line of chunk.split('\n')) { ... JSON.parse ... } // ❌ 行边界完全没管
    } catch { /* 忽略解析错误的行 */ }                        // ❌ 把证据也一起吞了
```

**`stream: true` 挡住了字节边界，行边界没管。** 一条 `data: {...}` 被切成两片时，
两半都不是合法 JSON，`catch {}` 把它们**双双静默丢弃** —— 那个 token 就没了。

表现是**偶发掉字**：不报错、不断流、日志里什么都没有，只在响应较长或网络抖动时出现，
不可复现。**这里的 `catch {}` 不是容错，是把 bug 藏起来。**

修法：抽出 `chat/sseLines.mjs`（跨分片行缓冲，含孤立 CR 的扣留处理），
两处调用点共用；`catch` 保留但含义变了，注释写清「现在只兜非 JSON 的心跳行」。

**顺带给后端开了单元测试**：12 条，用 Node 内置的 `node:test`，**零新增依赖**
（后端原本只有需要连库的冒烟脚本）。跑法 `npm run test -w ai-fashion-server`。
其中一条是反证：用旧写法对切开的两半 `JSON.parse` 必定抛异常 ——
**证明这个 bug 真实存在，不是臆想的。**
