## Context

### 为什么需要这一份

Pinterest 那份计划解决的是「简历上写不出性能优化和长列表」。它没覆盖的是**本岗 JD 独有的三个点**：

| JD 原文                                             | 现状                                       |
| --------------------------------------------------- | ------------------------------------------ |
| 职责 2：移动端开发，不只有移动 Web、小程序多端      | ✅ 已有（uni-app 双端 + MV3 扩展）         |
| 要求 3：有 NodeJS/Java 开发经验，或有移动端开发经验 | ✅ 三条线全有，这是本岗最大赌注            |
| 要求 4：深刻理解可用性、**可访问性**                | ❌ **完全没做过**                          |
| 职责 1：页面搭建、中后台低代码等场景                | ⚠️ 只有 vue-admin 风格的电商平台，会被打折 |

加上题库记录的阿里侧重：**工程化（Monorepo / 微前端）+ 状态管理 + Node.js（SSR）**。
工程化已强（多包仓库 + 扁平配置分块注入 globals），**状态管理与 SSR 是空的**。

### 最大的一个洞

三个 AI 接口（`/chat/stream`、`/chat/tools`、`/chat/rag`）**前端一次都没调过**。
全前端（含 admin）搜这三个路径零命中，`miniapp/src/api/ai/index.ts` 只有
`/api/style-report`、`/api/scene-outfits`、`/api/chat`（裸对话，不带 RAG、不带流式）。

这意味着：**你这半年做的 AI 纵深 100% 在后端。** 投前端岗时，这些是加分项但不是主证据；
而真正属于前端的那一段（流式渲染、工具调用可视化、Markdown 容错）一行都没有。

## 批次 1 · 前端接上流式对话（最高性价比）

### 为什么这条排第一

| 维度 | 收益                                                                      |
| ---- | ------------------------------------------------------------------------- |
| 简历 | 把一句假话变成真话，且不用删任何已有内容                                  |
| 题库 | 命中「🔥 SSE / WebSocket（考频 10，流式数据处理）」「WebSocket 重连策略」 |
| 岗位 | 前端岗唯一能证明「AI 应用的前端那一半我也做过」的证据                     |
| 成本 | 后端已经全通，只差客户端                                                  |

### 做什么

**1.0 先只做 H5 端。** 小程序端的请求接口不支持流式接收，微信另有分块接收方案但你没真机验证过——
**不验证就不做、不写**，这条结论保持不变。H5 端用浏览器原生的流式读取即可。

**1.1 分块边界处理（这是真正的技术点）。**
网络分片和 SSE 的消息边界不对齐：一个分片里可能有两条半消息，也可能半条消息跨两个分片。
必须维护一个缓冲区，按空行切分，最后不完整的那段留到下一片再拼。
**面试官问「你怎么知道要做这个」——因为不做，中文会乱码、JSON 会解析失败。**

**1.2 中途停止。** 用户点「停止生成」要能真的断开，后端那边已经监听了连接关闭并会中止模型调用。
**这一步是前后端咬合的，能讲：不是前端假装停了，是真的把后端的账单也停了。**

**1.3 异常重连（可选，做了更完整）。**
断线后能不能接着上次的位置继续，取决于服务端支不支持断点。
**如果不做，就不要在简历里写「异常重连」。** 只写做到的。

### 验收标准

- [ ] H5 端能看到逐字输出
- [ ] 人为把响应切成畸形分片（半条消息 / 两条挤一起），输出仍然正确
- [ ] 点停止，后端日志显示模型调用被中止
- [ ] 关掉页面，后端同样中止（这条现在就是通的，顺手验证）

### 产出的简历 bullet

> 前端接入流式对话：按 SSE 协议处理网络分片与消息边界不对齐（缓冲 + 空行切分 + 残片续拼），
> 支持中途停止并联动中止后端模型调用

## 批次 2 · 可访问性最小可信版

### 为什么必须做

JD 要求 4 原文：**「深刻理解可用性、可访问性」**。
你现在是零。被问到只能承认，而这是 JD 白纸黑字写的要求——**承认一条明写要求为零，比承认 SSR 没做过严重得多**。

不需要做全，需要做到**能讲清楚三件事 + 有一处真实改动**。

### 做什么（按成本从低到高）

**2.1 键盘可达（最基础，必做）。**
现在弹层、抽屉、自定义按钮大概率是 `<view>` 加点击事件——鼠标能点，键盘 Tab 不到、回车不触发。
挑**登录页 + 一个弹层**改：可聚焦、Tab 顺序正确、回车/空格能触发、Esc 能关。

**2.2 焦点管理（弹层必做，最能讲）。**
弹层打开时焦点要移进去，关闭时要还回触发它的那个元素；打开期间 Tab 不能跑到背景里去（焦点陷阱）。
**这条是 a11y 里最工程化的一条，讲出来含金量最高**，因为它和「弹层怎么管理状态」是同一个问题。

**2.3 语义与替代文本。**
图片有意义的给替代文本、纯装饰的显式标空；自定义控件补上角色与状态标注；
表单的标签和输入框关联起来。

**2.4 对比度自查。**
你有一套颜色变量，挑正文色 / 次要文字色 / 禁用态三组量一下对比度。
**大概率会发现次要文字色和禁用态不达标**——这正好是一条真实发现，比「我知道要 4.5:1」有说服力得多。

### 验收标准

- [ ] 登录页全流程可以**不碰鼠标**走完
- [ ] 弹层开关的焦点进出正确，打开期间焦点不逃逸
- [ ] 跑一次自动化检查（Lighthouse 的 accessibility 分项就够），记下改前改后
- [ ] 对比度自查表：哪几组不达标、改了哪几组、哪几组决定不改及原因

### 产出的简历 bullet

> 可访问性：弹层焦点陷阱与焦点归还、核心路径键盘可达、颜色对比度自查并修正 N 组不达标色值

⚠️ **不要写「符合 WCAG 2.1 AA」**——你没有做全量审计，这是无据的。写你真做的那几条。

## 批次 3 · 工具调用过程可视化

### 为什么

这是简历上那句「调用过程在前端可视化」的兑现，也是**AI 前端唯一能做在前端的部分**。
后端的工具调用循环已经写好（最多 5 轮），欠的是把每一轮的状态推给前端并渲染。

### 做什么

**3.1 后端把中间状态也推出去。** 现在工具那条路是最终文本一次性推（请求体里没开流）。
最小改法不是改成真流式，是**每一轮结束时推一条状态事件**：模型要调哪个工具、参数是什么、
执行结果摘要、当前第几轮。

**3.2 前端渲染成一个可展开的步骤条。** 折叠时只显示「正在查你的衣橱…」，
展开能看到每一轮的工具名、入参、返回摘要。

**3.3 Markdown 容错渲染（顺手做，题库点名）。**
流式输出时 Markdown 是不完整的——代码块的围栏可能只来了一半、列表可能断在中间。
直接渲染会整段闪烁或结构跳动。做法是渲染前补全未闭合的结构。
**这条是「AI 工程化」里最典型的前端问题，题库第五节点名要求。**

### 诚实边界（讲的时候必须带上）

- 工具调用这条路**目前仍不是真流式**，最终文本是一次性推的，我推的是每一轮的状态事件
- **Anthropic 的工具协议没接**，切过去会显式抛 501 并说明原因——这是我主动加的守卫，
  在这之前它会带着 OpenAI 的请求形状发到 Anthropic 地址，报一个看着像密钥问题的 404

## 批次 4 · 状态管理讲得出深度（可选）

阿里侧重三件套之一，但你现在对 Pinia 只能讲「我用了」。
不需要重构，需要**找到项目里一个真实的状态管理问题并解决**。候选：

- **跨页面状态同步**：衣橱页改了数据，详情页 / 首页的缓存要不要失效、怎么失效
- **持久化边界**：哪些状态该存本地、哪些不该（登录态该，列表缓存不该——会看到过期数据）
- **store 之间的依赖**：有没有出现 A store 直接读 B store 的内部状态

挑一个，写清「原来什么问题 → 怎么改 → 代价是什么」，就是一条可讲的 bullet。

## 明确不做

| 项                    | 为什么不做                                                                   | 被问到怎么答                                                                                                                                                                  |
| --------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SSR**               | 成本极高，且 uni-app 这条链路做 SSR 意义不大                                 | 「没做过。我知道它是把首屏渲染挪到服务端，为首屏和 SEO。我做过最接近的是首屏性能——把首屏最大元素从接口依赖改成静态内容，让首屏时间不再是网络的函数，但那和 SSR 不是一回事。」 |
| **微前端**            | 你的三个包是一个团队一个人，微前端解决的是多团队独立部署，**你没有那个问题** | 「没做过。它解决的是多团队独立开发部署、技术栈隔离。我的项目是单人多包仓库，用工作区 + 统一工具链就够了，上微前端是给自己找麻烦。」                                           |
| **低代码 / 页面搭建** | 从零做一个搭建引擎不是一两周的事                                             | 把话题转到电商运营管理平台的 ACL 菜单渲染——**菜单由配置驱动动态生成**，这是和低代码同源的思路                                                                                 |
| **React**             | 学一门框架换不来深度                                                         | 「没用过 React。Vue3 的响应式、编译、组合式 API 我能讲到原理层。框架我可以学，但我现在能讲透的是 Vue。」                                                                      |
| **webpack**           | 你用的是 Vite                                                                | 「没用过 webpack，用的是 Vite。开发态走原生 ESM 按需编译不打包，生产态 Rollup。webpack 的 loader/plugin 机制我只是读过，没实践过。」                                          |
