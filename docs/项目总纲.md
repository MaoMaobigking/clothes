## 1. 项目定位与满配架构

### 1.1 一句话定位（简历/面试开场就这么说）

> **「灵犀」AI 穿搭助手** —— 一套微信小程序 AI 穿搭系统：
> **C 端小程序**（身形测试 → AI 出专属穿搭报告 → 衣橱/商城/AI 顾问）
> ＋ **B 端管理后台** ＋ **AI 工程化后端**（结构化输出 / 流式 / 工具调用 / MCP / RAG，Node 或 Python-FastAPI）。

记住三个关键词——**双端（C+B）、真上线、AI 工程化**。这三个词是本项目区别于"网上抄的 demo"的地方。

### 1.2 满配架构图

```text
┌──────────────────────────────────────────────┐
│ C端：微信小程序  uni-app / Vue3 / TS / Pinia      │ ← 你最强，主交付
├──────────────────────────────────────────────┤
│ B端：管理后台   Vue3 + Element Plus              │ ← 凑成 C+B 双端
├──────────────────────────────────────────────┤
│ 后端：Node + 轻量三层 + JWT 鉴权                  │ ← 分层 + 登录鉴权
│         routes → services → repositories        │
├──────────────────────────────────────────────┤
│ AI 工程层：结构化输出 / 流式 / 工具调用 / MCP / RAG │ ← ★护城河，含金量最高
├──────────────────────────────────────────────┤
│ 数据库：MySQL（换掉 SQLite，用你熟的）             │ ← 表设计/索引/事务
├──────────────────────────────────────────────┤
│ 部署：小程序 + 后端上云 + HTTPS 域名               │ ← "真上线过"
└──────────────────────────────────────────────┘
```

**数据怎么流（一句话）**：小程序/后台 → HTTP 请求 → Node 后端（分层 + 鉴权）→ 调 MySQL 存取 / 调 AI 大模型 → JSON 返回前端。

## 2. 战略与现状 ★

### 2.1 北极星愿景（2026-07-16）

- **最终交付形态**：一个**双端（小程序 + 后台）、真数据库（MySQL）、有登录鉴权、有 AI 工程化深度、真上过线**的完整系统。这已是应届里的"满配简历项目"，足够对齐 30 万的前端 / 全栈 / AI Agent 岗。

### 2.2 战略转向：收敛做实（2026-07-21，★当前有效）

**一句话总纲**：**把要留的部分，一块块手敲重建 + 顺手做实，变成面试戳不穿、每行你都能亲口讲的代码。** 这样"提升能力"和"冲击大厂"是同一件事。**收敛做深 > 铺摊子。**

**核心诊断**：冲击大厂，这个项目的病**不是功能少，而是"虚"**——摊子太大、一半是壳、还有一块（Python）讲不了。面试官必定深挖（"MCP 现场调一个""登录鉴权怎么做""为什么两个后端"），一挖壳就碎。

**锁定的决策（2026-07-21 已拍板）**：

- **主线** = `web`（Vue3 H5）+ `server`（Node Express）。做深做实做到戳不穿。
- **Python `ai-server`** = 如实标注为"练手翻译版 / 实验分支"，**不投入、不进主线故事**（但它是"多语言后端"的加分素材，别删）。
- **后端框架** = **保留 Express，不重写 NestJS**（把现有壳补成真，省时间、先能讲；NestJS 留作秋招前若有余力的可选升级）。
- **miniapp / admin** = 降级为附加/原型，主线故事不依赖它们（admin 可在"拔高层"被救活成"AI 调用监控台"）。

### 2.3 诚实现状盘点

**monorepo `ai-fashion-studio` 五个子项目：**

| 模块 | 是什么 | 完成度 | 能亲口讲清吗 | 现状要害 |

**"玩具感"的三个根因（必须先修）：**

1. 🔴 **没有"用户"概念——所有人共用一个衣橱**。JWT/越权注释都写了，但运行时 SQLite 只建了一张 `garments` 表、无 `user_id`；微信登录是 mock，`userId` 写死=1；衣橱 GET 里 `// TODO: 按 userId 过滤` 实际返回所有人数据。→ 登录/鉴权/越权全是"演的"，一问"两个用户怎么隔离"当场穿帮。

## 4. 数据模型（MySQL · 7 张核心表）

**设计原则**：**把 AI 生成的结果存进数据库**（标 ★ 的表）。存了才是产品，不存只是调 API。

```text
users              用户（id / 昵称 / 头像 / openid / 创建时间）
        │
        ├── body_profiles     身形档案（5 步测试：风格/肤色/脸型/体型/偏好）
        ├── style_reports   ★ AI 风格报告（测试答案 + AI 分析 JSON + 时间）
        ├── garments          衣橱（名字/分类/颜色/图片URL/是否收藏）
        ├── outfits           搭配方案（一套搭配）
        │        └── outfit_items   搭配含哪几件衣服（关联 garments）
        └── chat_sessions   ★ AI 顾问会话
                 └── chat_messages ★ 每条消息（role + 内容 + 时间）
```

**建表要点（面试会问）**：
- 每张业务表都带 `user_id` 外键 → 支撑"越权控制：不是本人数据返回 404"。
- 高频查询字段加索引（`garments.user_id`、`chat_messages.session_id`）。
- 图片**只存 URL**，不把图片塞进数据库。
- `style_reports.answers`/`result`、`chat_messages` 用 JSON 字段存 AI 结构化输出。

**完整建表 SQL（唯一事实来源，运行时 schema 要对齐这份）：**

```sql
-- users
CREATE TABLE users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  openid VARCHAR(64) UNIQUE,
  nickname VARCHAR(64),
  avatar_url VARCHAR(512),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- body_profiles  身形档案
CREATE TABLE body_profiles (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  skin VARCHAR(32),          -- 肤色
  face VARCHAR(32),          -- 脸型
  body_type VARCHAR(32),     -- 体型
  height DECIMAL(5,1),
  weight DECIMAL(5,1),
  bmi DECIMAL(4,1),
  bust DECIMAL(5,1),
  waist DECIMAL(5,1),
  thigh DECIMAL(5,1),
  calf DECIMAL(5,1),
  preferences JSON,          -- 偏好
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- ★ style_reports  AI 风格报告
CREATE TABLE style_reports (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  answers JSON,              -- 测试答案
  result JSON,               -- AI 分析结果 (summary/radar/palette/recommendations/tips)
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- garments  衣橱
CREATE TABLE garments (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  name VARCHAR(128) NOT NULL,
  category VARCHAR(32),
  color VARCHAR(32),
  image_url VARCHAR(512),
  is_fav BOOLEAN DEFAULT FALSE,
  brand VARCHAR(64),
  season VARCHAR(32),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id),
  INDEX idx_user_id (user_id)
);

-- outfits  搭配方案
CREATE TABLE outfits (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  title VARCHAR(128),
  scene VARCHAR(32),
  reason TEXT,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- outfit_items  搭配含哪几件衣服
CREATE TABLE outfit_items (
  id INT AUTO_INCREMENT PRIMARY KEY,
  outfit_id INT NOT NULL,
  garment_id INT NOT NULL,
  sort_order INT DEFAULT 0,
  FOREIGN KEY (outfit_id) REFERENCES outfits(id) ON DELETE CASCADE,
  FOREIGN KEY (garment_id) REFERENCES garments(id)
);

-- ★ chat_sessions  AI 顾问会话
CREATE TABLE chat_sessions (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  title VARCHAR(128),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- ★ chat_messages  每条消息
CREATE TABLE chat_messages (
  id INT AUTO_INCREMENT PRIMARY KEY,
  session_id INT NOT NULL,
  role ENUM('user','assistant') NOT NULL,
  content TEXT NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (session_id) REFERENCES chat_sessions(id) ON DELETE CASCADE,
  INDEX idx_session_id (session_id)
);
```

> 注：`schema.sql` 里其实已设计好这些表，但**运行时的 SQLite 没用它**（只建了一张无 `user_id` 的 garments）。修根因一/二的核心就是"让运行路径真正用上这份 schema"。

## 5. AI 工程化护城河 ★

这是抬高上限的核心。按性价比顺序做，每个都是一个面试故事。

### 5.1 先分清"两种框架"（别再搞混）

| 框架类型 | 例子 | 用不用 | 干嘛的 |
|---|---|---|---|
| **AI 编排框架** | LangChain / LangGraph / LlamaIndex | ❌ **不用** | 帮你拼 AI 逻辑，会把原理藏起来，面试讲不清 |
| **Web 框架** | Express（在用）/ FastAPI / Spring Boot | ✅ **必须用** | 收发 HTTP 的地基，没人手写 HTTP 服务器 |

> **一句话**：Web 框架管"路"（Express/FastAPI，照用），AI 逻辑管"脑"（手写，别让 LangChain 代劳）。
> 数据佐证：2026 年"简历只有 LangChain"是减分项，面试必问"你不用 LangChain 做过什么"。**手写才是加分。**

### 5.2 核心五件套（AI 逻辑手写，每个都是面试故事）

| # | 能力 | 是什么 | 面试怎么讲 |
|---|---|---|---|
| 1 | **结构化输出** | AI 稳定返回固定 JSON（风格报告），不是乱文字 | "我用 JSON Schema 约束模型输出，前端稳定解析，校验失败自动重试" |
| 2 | **流式输出（SSE）** | AI 顾问对话像打字机逐字出 | "我做了 SSE 流式，首字延迟低；流式结束后完整消息存库，下次能看历史" |
| 3 | **工具调用（手写）** | AI 能调后端函数（查衣橱/查天气再推荐） | "我手写 tool-calling 循环：模型请求工具→我执行→喂回→循环到结束" |
| 4 | **MCP** | 把能力包成标准化 MCP 工具（字节 AIDP 考点） | "我用 MCP 协议暴露工具，模型即插即用、动态发现调用" |
| 5 | **RAG + 向量库** | 基于知识库回答（先检索再答，减少胡编） | "文档切块→向量化→检索 top-K→拼进 prompt" |

**最低目标**：1、2、3（从"调了个 AI 接口"升级到"做过 AI 工程"）。
**差异化目标**：4（MCP）+ 5（RAG）。时间紧不用全满，做出 **2~3 个能深聊的点**就够撑差异化。

### 5.3 关键能力"壳"诊断与修法（简历上写了、一追问就露馅的，必须先修真）

1. **tool-calling 的"流式"是假的**：`aiChatWithTools` 最后 `onChunk(整段文本)` 一次性吐（`aiService.mjs:708-710`）。
   → 拿到最终 text 后走一次流式补全逐字推；或工具执行阶段推"正在查天气…"状态事件。
2. **tool-calling 只有 OpenAI 分支**：`provider=anthropic` 时工具不可用。
   → 补 Anthropic 分支，否则"多厂商"卖点在工具场景是破的。
3. **工具/数据写死**：天气 mock 了 4 城；MCP 的 `search_garments` 读 `seed.json`、`get_user_profile`/`generate_style_report` 返回硬编码字符串（`mcp/server.mjs:100-111`）。
   → 天气接真 API（和风/OpenWeather 免费档），哪怕一个城市；MCP 工具改调后端真实 service。
4. **RAG 是关键词检索非语义向量**：TF-IDF + bigram + 余弦（`ragService.mjs`），换个说法就检索不到。
   → **二选一**：① 诚实——话术改"TF-IDF 关键词检索增强"，讲清为什么够用（成本低、无外部依赖）；② 升级——换真 embedding（`text-embedding-3-small`）+ 向量库（pgvector/Chroma/Qdrant），才配叫"向量化 RAG"。
5. **RAG 没有相关度阈值**：永远返 top-3，哪怕全不相关。
   → 加阈值：score 低于阈值丢弃；一条都不够就走普通对话，别硬塞。

### 5.4 Python 门票（用本项目练，成本最低）

- **为什么碰**：岗位数据显示"纯 AI Agent / 大模型应用工程师"岗**大多默认要 Python**（90%+ AI 工作在 Python）。不会 Python，这批更高天花板的岗基本关门。
- **要多深**：只需 **intermediate**——函数/类/异常/`asyncio`/FastAPI，能读写多文件项目即可。你已精通 JS/TS，这是**迁移不是重学，2~4 周晚上的事**。
- **怎么练**：把 **AI 工程层用 Python + FastAPI 再写一版**，前端和数据库不动。
- **岗位映射**：只会 TS/Node → 投"AI 应用/全栈（前端向）"；补了 Python → "AI Agent 工程师"也能投，**岗位池翻倍**。
- 注意：**FastAPI 是 Web 框架（Python 版 Express）**，属"必须用"那类，跟"不用的 LangChain"是两回事。
- ⚠️ 当前状态：`ai-server` 开箱报错、无 `requirements.txt`、和 Node 完全重复、没接线。按第二代战略它**先标注为"实验分支"，等 Node 版 A/B/C 跑通再回头做**，别让它拖当前进度。

## 9. 三条铁律（贯穿始终）

1. **不用 AI 编排框架（LangChain），Web 框架（Express/FastAPI）照用** —— AI 逻辑手写才讲得出原理；讲得出原理 > 用得了框架。
2. **能演示 + 能讲架构 + 能深聊 AI**，三者缺一不可（光能跑不够）。
3. **前端和 AI 往深做，后端/数据/部署做到"会、能讲流程"就停** —— 别样样松。
4. **每一步动代码前先跟用户确认**（本纲只排方向，不含代码）。
