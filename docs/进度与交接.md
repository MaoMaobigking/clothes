## 本地环境（换机或重启后照这个来）

```bash
# 1. MySQL 容器（已建好，重启机器后只需 start）
docker start lingxi-mysql
# 首次创建：
#   docker run -d --name lingxi-mysql -p 3308:3306 \
#     -e MYSQL_ROOT_PASSWORD=<密码> -e MYSQL_DATABASE=lingxi -e TZ=Asia/Shanghai \
#     --restart unless-stopped mysql:8.0 \
#     --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci

# 2. 建表（幂等，随时可跑）
cd server && npm run db:init

# 3. 起后端
npm run dev            # 8787

# 4. 验收
npm run db:check       # service 层：真用户/真落库/真隔离
npm run check:http     # HTTP 层：状态码/鉴权/请求体防御（需先起后端）
```

`server/.env` 必填项见 `server/.env.example`（`MYSQL_*` + `JWT_SECRET` 缺了起不来）。

**重启后端的坑**：Windows 上 `npm run dev` 的 node 子进程不会随终端退出而死，
旧进程占着 8787 会让你以为"改了代码没生效"。先清端口：

```bash
netstat -ano | grep ":8787" | grep LISTENING   # 拿 PID
taskkill //F //PID <PID>
```

## 踩过的坑（值得记，面试也能讲）

1. **派生标识符别用截断，要用定长哈希。**
   开发态 mock openid 原本是 `hex(code).slice(0, 16)`，而 `"devcode_"` 这 8 个字符
   hex 出来正好占满 16 位 —— 真正用来区分用户的后缀全被截掉，两个不同 tag 拿到同一个
   `userId`。表面看是"数据隔离失效"，实际是**登录阶段就把两个人认成了一个人**。
   已改 sha256。教训：公共前缀 + 截断 = 必然撞车。

2. **越权控制要放在 SQL 里，不要"查出来再在 JS 里比对 user_id"。**
   后者漏写一个 `if` 就漏数据；前者打不中就是 0 行，天然安全。

3. **返 404 不返 403。** 403 等于告诉攻击者"这个 id 存在"，可被枚举。

4. **兜底默认密钥是真实事故来源。** `process.env.X || '硬编码值'` 一旦忘配环境变量，
   线上就在用一个写在开源代码里的密钥签 token。启动失败比静默用弱密钥安全得多。

5. **事务里必须用 `conn.execute`，不能用池方法** —— 否则跑在池里另一条连接上，
   根本不在这个事务里。`withTransaction` 的注释里记了。

6. **批量插入 `VALUES ?` 只能用 `conn.query`，不能用 `execute`** ——
   预处理语句无法展开数组。
