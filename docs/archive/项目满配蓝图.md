## 0. 一句话定位（简历/面试开场就这么说）

> **「灵犀」AI 穿搭助手** —— 一套微信小程序 AI 穿搭系统：
> **C 端小程序**（用户做身形测试 → AI 出专属穿搭报告 → 衣橱/商城/AI 顾问）
> ＋ **B 端管理后台** ＋ **AI 工程化后端**（结构化输出 / 流式 / 工具调用 / MCP / RAG，可 Node 或 Python-FastAPI）。

记住三个关键词：**双端（C+B）、真上线、AI 工程化**。这三个词是这个项目区别于"网上抄的 demo"的地方。

## 4. 数据模型（MySQL，7 张核心表）

设计原则：**把 AI 生成的结果存进数据库**（标 ★ 的表）。存了才是产品，不存只是调 API。

```text
users              用户（id / 昵称 / 头像 / openid / 创建时间）
        │
        ├── body_profiles     身形档案（5步测试：风格/肤色/脸型/体型/偏好）
        │
        ├── style_reports   ★ AI风格报告（测试答案 + AI分析JSON + 时间）
        │
        ├── garments          衣橱（名字/分类/颜色/图片URL/是否收藏）
        │
        ├── outfits           搭配方案（一套搭配）
        │        └── outfit_items   搭配含哪几件衣服（关联 garments）
        │
        └── chat_sessions   ★ AI顾问会话
                 └── chat_messages ★ 每条消息（role: user/assistant + 内容 + 时间）
```

**建表要点（面试会问）**：
- 每张业务表都带 `user_id` 外键 → 支撑「越权控制：不是本人数据返回 404」。
- 高频查询字段加索引（如 `garments.user_id`、`chat_messages.session_id`）。
- 图片**只存 URL**，不把图片本身塞进数据库。
- `style_reports.answers` / `result`、`chat_messages` 这类用 JSON 字段存 AI 结构化输出。

## 5. AI 工程化（护城河，重点）

这是抬高上限的核心。按性价比顺序做，每个都是一个面试故事。

### 5.1 先分清"两种框架"（别再搞混）

| 框架类型 | 例子 | 用不用 | 干嘛的 |
|---|---|---|---|
| **AI 编排框架** | LangChain / LangGraph / LlamaIndex | ❌ **不用** | 帮你拼 AI 逻辑（prompt、工具调用循环），会把原理藏起来，面试讲不清 |
| **Web 框架** | Express（现在在用）/ FastAPI / Spring Boot | ✅ **必须用** | 收发 HTTP 请求的地基，跟 AI 无关，没人手写 HTTP 服务器 |

> **一句话**：Web 框架管"路"（Express/FastAPI，照用），AI 逻辑管"脑"（手写，别让 LangChain 代劳）。
> 数据佐证：2026 年"简历只有 LangChain"是减分项，面试必问"你不用 LangChain 做过什么"。手写才是加分。

### 5.2 核心能力（AI 逻辑这块自己手写）

| # | 能力 | 是什么 | 面试怎么讲 |
|---|---|---|---|
| 1 | **结构化输出** | 让 AI 稳定返回固定 JSON（风格报告），不是乱文字 | "我用 JSON Schema 约束模型输出，保证前端稳定解析" |
| 2 | **流式输出** | AI 顾问对话像打字机逐字出（SSE） | "我做了 SSE 流式，首字延迟低、体验好" |
| 3 | **工具调用 / Function Calling** | AI 能调用你后端的函数（查衣橱/查天气再推荐） | "我手写了 tool-calling 循环：模型请求工具→我执行→喂回结果→循环到结束" |
| 4 | **MCP** | 把能力包成 MCP 工具（字节 AIDP 考过，差异化） | "我用 MCP 协议暴露工具，模型即插即用" |
| 5 | **RAG + 向量数据库** | 让 AI 基于"你的知识库"回答（穿搭知识/单品库先检索再答） | "我做了 RAG：文档切块→向量化→检索→拼进 prompt，减少胡编" |

**最低目标**：1、2、3 —— 从"调了个 AI 接口"升级到"做过 AI 工程"。
**差异化目标**：4（MCP）+ 5（RAG）—— 直接对齐大厂 AI 应用岗核心考点。

> 时间紧不用全满，做出 **2~3 个能深聊的点**就够撑差异化；RAG 有余力再上。

### 5.3 Python 门票（用本项目练，成本最低）

**为什么要碰 Python**：岗位数据显示"纯 AI Agent 工程师 / 大模型应用工程师"岗**大多默认要 Python**（90%+ 的 AI 工作在 Python）。不会 Python，这批更高天花板的岗基本关门。

**要多深**：只需 **intermediate（中级）**——函数/类/异常/`asyncio`/FastAPI，能读写多文件项目即可。你已精通 JS/TS，这是**迁移不是重学，2~4 周晚上的事**。

**怎么练（不另起炉灶）**：把 **AI 工程层用 Python + FastAPI 再写一版**，前端和数据库不动。

```text
前端/小程序 ──HTTP──> Python(FastAPI) AI 服务  ← 结构化输出/流式/工具调用/RAG
                     （或继续用 Node，二选一都能讲）
```

一箭双雕：练了 Python，又多一个"技术选型 / 多语言后端"的面试故事。

> **岗位映射**：只会 TS/Node → 投"AI 应用 / 全栈（前端向）"岗；补了 Python → "AI Agent 工程师"岗也能投，**岗位池翻倍**。
> 注意：这里的 **FastAPI 是 Web 框架（等于 Python 版的 Express）**，属于"必须用"那类，跟 5.1 里"不用的 LangChain"是两回事。

## 6. 每块「做到什么程度 + 面试怎么讲」速查

- **小程序前端**：组件化、请求统一封装、Pinia 管登录态、加载/错误状态处理。
  → "我做了请求层统一封装和错误兜底，组件按业务拆分复用。"
- **B 端后台（Element Plus）**：衣服库管理、用户数据查看、简单图表。
  → "一套系统我做了 C 端小程序 + B 端后台，双端打通。"
- **后端分层**：routes 收发、services 业务、repositories 只碰 SQL。
  → "后端按 Controller-Service-DAO 分层，类似 Spring 的思路。"
- **JWT 鉴权**：登录发 token，接口校验，非本人数据返 404。
  → "我做了 JWT 鉴权和越权控制，不是本人的数据一律 404。"
- **MySQL**：表设计带外键/索引，关键写操作用事务。
  → "衣橱和搭配是关联表，高频查询加了索引，下单类操作用事务保证一致性。"
- **部署**：后端上云、配 HTTPS 域名、小程序配合法域名。
  → "我真上线过：后端部署到云服务器，小程序走 HTTPS 调线上接口。"

## 7. 落地路线图（不打乱现在的进度）

```text
1. 搬完小程序页面能演示              ← 现在在做（P2 组件 / P3 五个 tab 页）
2. 后端轻量三层 + 换 MySQL + JWT 登录   ← 后端广度 & 你熟的 MySQL
3. AI 工程化核心：结构化输出 → 流式 → 工具调用   ← ★上限所在，重点投入（手写）
4. Python 门票：用 FastAPI 把 AI 层再写一版      ← 开门票，ROI 最高（intermediate 即可）
5. 进阶考点：MCP + RAG（向量数据库）            ← 差异化，对齐大厂 AI 应用岗
6.（有余力）Element Plus 管理后台               ← C+B 双端加分
7. 部署上线 + HTTPS 域名                       ← "真上线过"
```

**优先级**：1、2 必做；3 是上限所在，重点投入；4 强烈建议（岗位池翻倍）；5 差异化；6 有余力；7 收尾。

## 9. 三条铁律（贯穿始终）

1. **不用 AI 编排框架（LangChain），Web 框架（Express/FastAPI）照用** —— AI 逻辑手写才讲得出原理；讲得出原理 > 用得了框架。
2. **能演示 + 能讲架构 + 能深聊 AI**，三者缺一不可（光能跑不够）。
3. **前端和 AI 往深做，后端/数据/部署做到"会、能讲流程"就停** —— 别样样松。
