## 总览：为什么是这个顺序

三块有依赖关系，排错了会返工：

```
🅐 根基（真用户 + 落库）
      │  图片要按用户存、试衣历史要落库、AI日志要落库 —— 全依赖它
      ▼
🅑 视觉（图片管线 + 拍照打标签 + 虚拟试衣）   ← 最去"玩具味"
      │
      ▼
🅒 AI 深度（可观测 + 评测 + 缓存 + 工程规范）  ← 简历最值钱，收尾
```

**关键交汇点 `aiClient`**：一层"给所有 AI 调用统一加超时/日志/重试"的封装。它在 🅐 起头（先加超时+日志），在 🅒 补全（重试+成本统计+看板）。**做一次，两阶段都受益**，所以放最前面顺手做。

**总周期估计**：3 阶段约 2~3 周（晚上投入为主，配合白天实习 = AB 并行）。

## 🅐 阶段一 · 根基：真用户 + AI 结果落库

> **目标**：把现在"演的"（登录、越权、AI 结果）变成"真的"。这是所有后续功能的地基。

**现状（对着代码）**：
- 运行时的 SQLite 只建了 `garments` 一张表、且没有 `user_id` 列（`server/db.mjs:29-44`）；`schema.sql` 里其实设计好了 8 张表，但运行路径没用它。
- 微信登录是 mock，`userId` 永远写死 = 1（`server/services/authService.mjs:24-25`）。
- 衣橱 GET 里写着 `// TODO: 按 userId 过滤`，实际返回所有人的数据（`server/routes/garments.mjs:22-24`）。
- 代码里**没有任何 INSERT** 把风格报告 / 对话存进库——AI 结果生成完就丢。
- MySQL 的 `add` 语句 9 列只给了 8 个占位符（`server/db.mjs:143-147`），从没跑通过。

### A1. 让运行数据库真正用上 `schema.sql`（建全表 + 加 user_id）
- [ ] 运行时建出 `users` 表，`garments` 加 `user_id` 列（对齐 `schema.sql` 的设计，而不是只建一张 garments）
- [ ] **改哪**：`server/db.mjs`（建表逻辑）、`server/schema.sql`（作为唯一事实来源）
- **为什么**：没有 user 和 user_id，"数据隔离"根本无从谈起

### A2. 越权控制落到 SQL（不是本人数据返 404）
- [ ] 衣橱查询一律带 `WHERE user_id = ?`；删除/改收藏用 `WHERE id=? AND user_id=?`，`affectedRows===0` 就返 404（不是 403，防枚举）
- [ ] **改哪**：`server/repositories/garmentRepo.mjs`、`server/services/garmentService.mjs`（把 `req.userId` 透传下去）、`server/routes/garments.mjs`（去掉那个 TODO）
- **面试话术**："越权控制我落在 SQL 层，不是本人的数据一律 404。"

### A3. AI 结果落库（★ 玩具→产品最关键的一跳）
- [ ] 风格报告：Schema 校验通过后写入 `style_reports(user_id, answers, result)`
- [ ] 对话：进页面建 `chat_session`，每条消息落 `chat_messages`；**流式结束后把完整回复存库**（现在流式跑完就丢）
- [ ] 前端"我的"加两个入口：**历史报告**、**历史对话**（从库里读，不重新生成、不重新烧钱）
- [ ] **改哪**：`server/repositories/aiRepo.mjs`、`server/services/aiService.mjs`（生成成功后调 repo 存）、`server/routes/ai.mjs`、前端 `miniapp/src/pages/me/` 加两个列表页
- **面试话术**："AI 结果持久化到库，可回看、避免重复调用省成本——存了才是产品。"

### A4. 修 MySQL + 统一异步
- [ ] 修 `add` 的占位符 bug（9 列配 9 个 `?`）
- [ ] 统一走异步接口，SQLite 也用异步包装，消灭 sync/async 割裂
- [ ] 本地用 Docker 起个 MySQL 真跑一遍衣橱 CRUD
- [ ] **改哪**：`server/db.mjs`、`server/db/mysql.mjs`
- **面试话术**："数据库用我熟的 MySQL，表设计带外键/索引，连接池管理。"

### A5. 顺手起 `aiClient`（可观测的起点，🅒 会接着用）
- [ ] 包一层统一的 AI 调用函数：加**超时**（现在 Node 版 fetch 无超时，会挂死）、打一条**调用日志**（model / 耗时 / 成败）
- [ ] **改哪**：新增 `server/services/aiClient.mjs`，`aiService.mjs` 里的 fetch 都走它
- **为什么**：小成本，先把"仪表盘"的接口留好，阶段三补齐

**✅ 阶段一验收**：注册两个用户，各建各的衣橱，A 拿不到 B 的数据；风格报告和对话刷新后还在；MySQL 模式 CRUD 能跑。

## 🅑 阶段二 · 视觉/多模态：让穿搭 App 真的"看得见"

> **目标**：补上一个穿搭 App 最该有的视觉线——真实衣服图、拍照建衣橱、虚拟试衣。这是"最去玩具味"的一步。
> **前提**：依赖阶段一的"落库"（图片 URL、试衣历史要存）。

**现状**：全是 emoji + 渐变占位（`TileImage.vue`、`seed.json`），没有真实图片；前端请求层 `miniapp/src/api/ai.ts` 的 `request()` **没带 token、没 baseURL**，真机调不通。

### B1. 真图片管线（B2/B3 的地基）
- [ ] 图片走：前端上传 → 对象存储 → 存 CDN 的 URL（数据库只存 URL，不存图片本身）
- [ ] **选型**：推荐 **阿里云 OSS**（国内快、配微信小程序合法域名方便）；备选 Cloudinary（免费额度大、自带图片裁剪）
- [ ] 前端：拍照 / 相册上传 → 签名直传（后端只发一个上传凭证，图片不经过后端中转）
- [ ] **顺带修**：请求层加 baseURL（从环境变量读完整 https 域名）+ 请求拦截器自动带 `Authorization: Bearer <token>`（token 存 Pinia）
- [ ] **改哪**：`server` 加一个"发上传凭证"的接口、`miniapp/src/api/*`（请求层封装）、上传组件
- **面试话术**："图片走对象存储 + CDN，前端签名直传不经过后端，省带宽。"

### B2. 拍照自动打标签 + 自动抠图（★ 多模态，最推荐）
- [ ] 拍/传一张衣服照 → 视觉大模型输出品类/颜色/季节/风格的**结构化 JSON** → 自动填进衣橱表单
- [ ] **复用已有能力**：这正好用上你 `aiService.mjs` 里的**结构化输出 + Schema 校验**层，只是把入参从文字换成"图片 + 文字"
- [ ] 抠图：接 fal.ai 的 `birefnet` 或 remove.bg 免费额度（去背景，衣服图更干净）
- [ ] **改哪**：`server/routes/garments.mjs` 加 `/analyze` 接口、`server/services/aiService.mjs`（新增"图片入参"的结构化调用）、前端上传后调用 + 回填表单
- **面试话术**："我做了**多模态**——图片进、结构化 JSON 出，复用了我的 JSON Schema 约束层。这是从'文字 AI'到'多模态 AI'的升级。"

### B3. 虚拟试衣（招牌"哇"功能）
- [ ] 上传本人照 + 选一件衣服 → 生成上身效果图 → 存结果 + 历史
- [ ] **接托管 API，绝不自己训模型**：推荐 Replicate 的 `IDM-VTON` 或 fal.ai 的 try-on（也可 Kwai Kolors）
- [ ] **核心是"异步任务"**：生成慢（几十秒），要做 提交任务 → 轮询/回调 → 结果落库 → 前端展示 + 历史。加一张 `tryon_tasks` 表
- [ ] **省钱**：约 $0.1/次，必须配合阶段三的限流/积分，别被刷爆
- [ ] **改哪**：新增 `server/routes/tryon.mjs` + service、`tryon_tasks` 表、前端试衣页 + 历史
- **面试话术**："虚拟试衣是耗时 AI 任务，我做了异步化——提交后轮询状态、结果持久化、有历史记录，不阻塞用户。"

### B4.（可选，秀前端）衣橱数据分析
- [ ] 一个"衣橱洞察"页：品类占比、颜色分布、每月新增、单件成本、最少穿的 5 件
- [ ] 用你**已经装了的 ECharts** + 几条 SQL group by，正好塞进 B 端 Element Plus 后台凑"双端"
- **面试话术**："我用数据可视化做了衣橱洞察，体现产品思维。"

> ⚠️ **平台坑（重要）**：`uni.request` 不支持 SSE 流式，**小程序端的"打字机逐字"目前做不出来**。B 阶段先别指望在小程序里做流式；要么用微信的分块接收方案验证过再上，要么退化成"整段返回"。别在简历写"小程序端流式"直到真机验证过。

**✅ 阶段二验收**：能拍照建衣橱、衣橱里是真实衣服图、能选衣服试穿看到上身效果、试衣有历史。截图放出来"像个真穿搭 App"了。

## 🅒 阶段三 · AI 深度：可观测 / 评测 / 缓存 + 工程规范

> **目标**：给 AI 层装上"仪表盘"，凑成完整的 **AI 工程化（LLMOps）** 故事。配合你已有的手写管子，深度直接拉开差距。
> **全部手写、不引入 LangChain**（守铁律）。

**现状**：`aiService.mjs` 无重试、无成本统计；`ragService.mjs` 是 TF-IDF 关键词检索、无相关度阈值；无 `requirements.txt`/Dockerfile/CI/单测；`errorHandler` 把 `err.message` 原样返前端。

### C1. 可观测（接住 A5 起头的 aiClient）
- [ ] `aiClient` 补齐：**指数退避重试** + 记录 model / tokens / 耗时 / 成败 到 `ai_logs` 表
- [ ] B 端后台加一个看板：调用次数、平均延迟、token 消耗、失败率（ECharts）
- **面试话术**："我能说出上周调了多少次、平均延迟多少、花了多少钱——AI 调用是可观测的。"

### C2. 评测（Evals）
- [ ] 攒 ~20 条金标准（输入 → 期望要点），写个打分脚本，改 prompt 前后跑分对比
- [ ] prompt 纳入版本管理（放代码里、有变更记录）
- **面试话术**："改 prompt 靠数据不靠感觉，有回归——避免修好一个问题、弄坏十个。"

### C3. 护栏（Guardrails）
- [ ] 输入：敏感词 / 越界话题过滤
- [ ] 输出：必须过 Schema 校验（你已有一半，补齐"不过就重试/兜底"）
- **面试话术**："输入输出都有护栏，防乱输入和乱输出。"

### C4. 语义缓存 + RAG 升级（选做）
- [ ] 语义缓存：问题算 embedding，命中相似历史直接返缓存，省重复烧钱
- [ ] RAG 加**相关度阈值**：score 太低的丢弃，一条都不够就走普通对话（现在永远塞 top-3，哪怕不相关）
- [ ] 有余力再把 TF-IDF 升级成真向量库（pgvector / Chroma），届时"向量化 RAG"才讲得实
- **面试话术**："相似问题走语义缓存，检索有阈值兜底，不硬塞不相关内容。"

### C5. 工程规范
- [ ] 补 `ai-server/requirements.txt`（Python 版现在没法一键装）
- [ ] 补 Dockerfile + GitHub Actions（build + test）
- [ ] service 层加 vitest 单测（几个关键函数即可）
- [ ] `errorHandler` 生产环境脱敏（别把上游原始报错返给前端）
- **面试话术**："项目能一键装、自动测，错误信息生产脱敏。"

**✅ 阶段三验收**：后台看得到 AI 调用统计；改 prompt 能跑评测看分数；CI 自动跑通 build+test。

## 别做什么（避免拖垮）

1. **别自己训模型 / 不复现 CV 论文**（IDM-VTON、GAN 那些）——试衣一律接托管 API。
2. **别上 LangChain/LangGraph**，把手写的好东西藏起来（守铁律）。
3. **别追功能数量**：5 个半成品 << 2 个能深聊能演示。集中打 B2、B3。
4. **3D 形象、社群**这类"炫但偏题"的，时间不够直接砍。
