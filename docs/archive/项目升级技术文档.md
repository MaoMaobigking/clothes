## 1. 三个根因（玩具感的真正来源，必须先修）

### 🔴 根因一：没有"用户"这个概念——所有人共用一个衣橱

你写了 JWT 登录、写了"越权控制返 404"的注释，但**实际数据根本没按用户隔离**：

- 运行时的 SQLite 只建了 **一张 `garments` 表，且没有 `user_id` 列**（`server/db.mjs:29-44`）。
- 微信登录是 mock，`userId` 永远写死 = 1（`server/services/authService.mjs:24-25`），没有 `users` 表、没查库。
- 衣橱路由挂了 `authRequired`，但 GET 里明晃晃写着 `// TODO: 按 userId 过滤`，**实际返回所有人的全部衣物**（`server/routes/garments.mjs:22-24`）；删除/收藏也没校验归属。

**后果**：登录、鉴权、越权控制目前全是"演的"。面试官问一句"两个用户怎么隔离数据"，当场穿帮。

**怎么修**（不难，是补齐不是重写）：
1. 运行的数据库真正建出 `users` 表，`garments` 加 `user_id` 列（`schema.sql` 里其实已经设计好了 7 张表，只是运行时的 SQLite 没用它——让运行路径用上这份 schema）。
2. `garmentRepo` 所有查询加 `WHERE user_id = ?`；`services` 把 `req.userId` 透传到 repo。
3. 越权控制落到 SQL：删除/改收藏时 `WHERE id=? AND user_id=?`，`affectedRows===0` 返 404。
4. 造 2 个测试用户，各建各的衣橱，验证 A 拿不到 B 的数据。

---

### 🔴 根因二：AI 结果用完即弃——"调了个 API"，不是"产品"

- `schema.sql` 里设计了 `★style_reports / ★chat_sessions / ★chat_messages` 三张表，但**运行时一张都没建，代码里也没有任何 INSERT**。
- 风格报告、情景推荐、AI 对话**全部无状态**：生成完直接返给前端，刷新即丢，历史报告/对话记录根本不存在。

这恰好踩在你自己蓝图里划的红线上——原话：**「存了才是产品，不存只是调 API」**。现在站在错误的一边。

**怎么修**：
1. `style-report` 生成成功 + Schema 校验通过后，写入 `style_reports(user_id, answers, result JSON)`。
2. 前端「我的-风格报告」从库里读历史，不是每次重新烧钱生成。
3. 对话：进页面先建 `chat_session`，每条 user/assistant 消息落 `chat_messages`；下次进来能看历史（这也是流式那段"结束后存库"该干的事，现在没干）。

> 这一步是"玩具→产品"最关键的一跳，也是投入产出比最高的：**改动集中在 3 个 service，前端多两个"历史列表"页**，但面试故事从"我调了 AI 接口"升级成"我做了有状态的 AI 产品，结果持久化、可回看、省重复调用成本"。

---

### 🔴 根因三：关键能力"看起来有，其实是壳"

这些最危险——**简历上写了、面试一追问就露馅**：

1. **tool-calling 的"流式"是假的**：`aiChatWithTools` 在最后 `onChunk(整段文本)` 一次性吐出（`aiService.mjs:708-710`），不是逐字流。`/chat/tools` 摆了 SSE 头却只发一个 chunk。
2. **tool-calling 只有 OpenAI 分支**：`provider=anthropic` 时工具直接不可用（其他 AI 函数都写了双分支，唯独这个漏了）。
3. **工具/数据是写死的**：
   - 天气 mock 了 4 个城市（`aiService.mjs:623-628`）。
   - MCP Server 的工具全是假的：`search_garments` 读 `seed.json` 不是真库、`get_user_profile`/`generate_style_report` 返回**硬编码字符串**（`mcp/server.mjs:100-111`）。MCP 是个"能连上但没接真业务"的空壳。
4. **RAG 是关键词检索，不是语义向量**：TF-IDF + bigram + 余弦（`ragService.mjs`）。没有 embedding、没有向量库。换个说法/同义词就检索不到。**面试说"我做了向量化 RAG"会被追问细节直接戳穿**——目前只能诚实说"我做了 TF-IDF 关键词检索"。
5. **RAG 没有相关度阈值**：永远返回 top-3，哪怕全不相关（score≈0 也塞进 prompt），反而可能误导模型。

**怎么修**（按性价比）：
1. tool-calling 改成**真流式**：拿到最终 text 后，走一次流式补全把答案逐字推给前端；或工具执行阶段也推"正在查天气…"的状态事件。
2. 给 tool-calling 补 **Anthropic 分支**（对齐其它函数），否则"多厂商"这个卖点在工具场景下是破的。
3. 天气接**真 API**（和风天气/OpenWeather 免费档），哪怕只接一个城市也是"真的"。MCP 工具改成**调你后端真实 service**，别读 seed.json。
4. RAG 二选一：
   - **要么诚实**：简历/话术改成"TF-IDF 关键词检索增强"，讲清为什么够用（成本低、无外部依赖）。
   - **要么升级**：换真 embedding（`text-embedding-3-small`）+ 向量库（pgvector / Chroma / Qdrant 选一个），这才配叫"向量化 RAG"，也是大厂考点。
5. RAG 加**相关度阈值**：top-K 里 score 低于阈值的丢弃；一条都不够就走普通对话，别硬塞。

## 2. 重要问题（P1，拉开档次的）

### 2.1 前端和后端"接不上"（小程序端的真实坑）

- **请求层不带 token**：`miniapp/src/api/ai.ts` 的 `request()` 只设了 `Content-Type`，**没有 `Authorization` 头**。而衣橱接口要鉴权 → 小程序端实际调不通。
- **没有 baseURL**：用的是相对路径 `/api/...`。**小程序不认相对路径，必须是完整 https 域名**。真机一跑就 404。
- **uni.request 不支持 SSE 流式**：`uni.request` 拿不到分块响应，**小程序端的"打字机流式"目前做不出来**（这是平台级限制，需要用 `wx` 的分块接收方案或改 WebSocket，或退化成"整段返回"）。这点现在没意识到，上真机会翻车。

**怎么修**：
1. 请求层统一封装：加 baseURL（从环境变量读）、请求拦截器自动带 `Authorization: Bearer <token>`（token 存 Pinia）、统一错误提示 + loading。
2. 流式：小程序端先用 `wx.request` 的 `enableChunked` / `onChunkReceived` 方案验证，跑不通就退化成非流式，别在简历上写"小程序端流式打字机"直到真机验证过。

### 2.2 MySQL 从没真正跑通

- `mysqlGarmentOps.add` **9 个字段只给了 8 个占位符**（`server/db.mjs:143-147`），一跑就 SQL 报错——说明 MySQL 路径从没被真正执行过。
- 同步/异步割裂：路由 `await` 的是同步函数，SQLite 侥幸能过；**切到 MySQL 会直接抛 `请使用异步接口`**（`db.mjs:174-189`）。
- 默认还是 SQLite，MySQL 是"写了但没用"的状态。

**怎么修**：统一走异步接口（`listGarmentsAsync` 那套），SQLite 也用异步包装，消灭 sync/async 分叉；修占位符 bug；本地用 Docker 起个 MySQL 真跑一遍 CRUD。**MySQL 是你熟、面试值钱的牌，别让它停在"半成品"。**

### 2.3 安全短板（能被一句话问倒 / 能被刷爆）

- `JWT_SECRET` 有硬编码默认值（`auth.mjs:9`），生产没配环境变量 = token 可伪造。
- CORS 全开 `cors()`（`index.mjs:29`），任何网站都能调你接口。
- **无限流**：AI 接口能被无脑刷 → 直接烧钱。至少加个简单的 rate limit。
- **无输入校验**：`req.body` 直接用，没有 zod/joi 之类。
- `errorHandler` 把 `err.message` 原样返前端（`errorHandler.mjs:17`），而 AI 报错里含上游接口原始返回，可能泄露内部信息。生产应脱敏。

### 2.4 没有 AI 成本 / 可观测性（"AI 工程化"故事的短板）

这是你护城河的一部分，现在缺得最明显：

- **无 token/成本统计**：调了多少、花了多少钱，一无所知。
- **无缓存**：同一份画像每次都重新生成报告 = 重复烧钱（配合根因二的"落库"，一起解决）。
- **fetch 无超时**（Node 版）：上游卡住 → 请求挂死。（Python 版有 60s 超时，Node 版没有，两版不一致。）
- **无重试/退避**：AI 偶发 5xx 直接失败。
- **无请求 id / 结构化日志 / 错误上报**。

**怎么修**：包一层 `aiClient`，统一加超时、重试（指数退避）、记录每次调用的 model/tokens/耗时/成功失败。这一层做出来，"AI 工程化"就有了真东西可讲（成本控制、稳定性、可观测）。
